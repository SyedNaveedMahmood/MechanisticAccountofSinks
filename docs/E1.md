# E1 — Cross-Scale & Cross-Architecture Sweep

**Experiment documentation: cross-scale code modifications + run protocol.**
Branch: `E4-with-tqdm` · commit `785bc3c` ("Add cross-scale support to all harnesses").

This document records (1) the code changes that make every intervention harness runnable
across model scales, and (2) the exact models, layer bands, precisions, and commands for
the E1 sweep. It is the reference for reproducing/auditing the cross-scale runs.

---

## 1. What changed in the code

Previously every harness hard-coded the paper's mid-layer band (layers 4–11, calibrated for
the 12-layer GPT-2 small) and only the Qwen harness accepted a `--dtype` flag. Deeper models
therefore reported the metric over an unrepresentative slice of their depth, and large
checkpoints had no precision control. Cross-scale support is now **uniform across all harnesses**.

### Central helper (`intervention_analysis.py`)
- **`compute_band(num_layers, layer_mode)`** returns the 0-indexed mid-layer band `[start, end)`:
  - `scaled` (default): excludes the **first 3 and the last layer** → `[3, num_layers − 1)`.
    For a 12-layer model this is exactly `[3, 11)` = the paper's layers 4–11, so **small models
    are byte-for-byte unchanged**; for deeper models it extends proportionally.
  - `fixed`: forces `[3, 11)` on every size (strict same-layer comparability).
- **`compute_bos_attention_metric(..., layer_start, layer_end)`** gained an optional explicit
  band override. When both are passed they take precedence over `layer_scope`; defaults preserve
  the original behavior, so the Table-1 reproduction path is untouched.

### Per-harness (`intervention_analysis.py`, `_opt`, `_neo`, `_qwen`, `residual_sink_analysis.py`)
- New CLI flag **`--layer-mode {scaled,fixed}`** (default `scaled`). The chosen band is threaded
  into the **mid**-band metric call only; the full-depth **`all_layers`** summary is still written
  alongside (so both views are always available).
- New CLI flag **`--dtype {float32,float16,bfloat16}`** (default `float32`) added where it was
  missing (GPT-2/OPT/Neo; Qwen already had it, plus `auto`). Applied at model load.
- E4 (`residual_sink_analysis.py`) additionally imports the shared `compute_band`, adds a robust
  massive-coordinate fallback (top-3 by |EPE₁| if <3 exceed 3σ), and records
  `model / dtype / layer_mode / band / massive_coords` to a per-seed `run_config.json`.

### Intervention (i) "Zero Top-3 Wk" — per-model massive-activation identification
Previously every harness zeroed a **blind fixed top-3** of |EPE₀| (GPT-2/OPT/Neo) or of the
position-0 token embedding (Qwen). That is only correct for models with exactly three massive
activations. The intervention now identifies the **massive activations** with the paper's own
outlier criterion — coordinates where `|EPE₀[d]| > mean + 3·std`, with a top-3 fallback if fewer
than three exceed it — **identical to E4's `identify_massive_coords`**, and zeroes exactly those
Wk columns in every layer. The random control **(j)** now zeroes an **equal number** of random
columns (was hard-coded to 3), so it remains a size-matched control at every scale.

- **Shared selector.** `intervention_analysis.select_massive_coords(signal, n_std=3.0, min_coords=3)`
  is imported by all four harnesses, so "massive" means the same thing everywhere. GPT-2/OPT/Neo
  compute `EPE₀ = p₀ + MLP⁽⁰⁾(p₀)` (input-independent, so the set is a fixed model property, derived
  once per run via a short dummy forward and threaded into (i)/(j)); Qwen (RoPE, no additive EPE)
  uses the position-0 token embedding per sentence.
- **Why it matters.** On `gpt2-medium` there are **6** massive coordinates
  (`[9, 238, 268, 428, 608, 580]`), not 3. Zeroing only the top-3 *under-ablates* and drives the
  BOS sink to **≈106% of baseline** (an increase — a clear artifact); zeroing all six restores the
  expected reduction (**≈37.5%** in a 3-sentence check). `opt-125m` (3 massive coords) gives (i)
  ≈43% vs. random-control (j) ≈100% — the paper's specificity contrast, intact cross-architecture.
- **Provenance.** Every `--mode dataset` run writes `run_config.json` next to its outputs recording
  the resolved geometry (`num_layers / num_heads / hidden_size / model_type`), dtype, band, and the
  exact massive coordinates + count zeroed by (i)/(j). A duplicated/mislabeled output is then
  immediately detectable (the geometry would not match the model) and the (i) identification is
  fully auditable — closing the two failure modes seen in the first sweep (duplicated `gpt2-large`
  data; unverifiable non-small `int_i` numbers).

### Multi-seed driver (`run_table1_multiseed.py`)
- Forwards **both** `--layer-mode` and `--dtype` to whichever harness it drives (previously
  `--dtype` was Qwen-only), plus `--engine` and `--remote` (see §7).
- **cwd fix.** The driver no longer depends on the caller's working directory. Harness paths
  resolve against the driver's own location, `--output-dir` is made absolute, and seeds run
  from the repo root. Previously, running the documented `cd cross_scale_and_architecture`
  command with `--model gpt2` failed: HuggingFace resolves a bare model id as a *local
  directory* when one exists, and `cross_scale_and_architecture/gpt2/` holds a
  documentation stub, so the hub id was shadowed
  (`OSError: ... no file named model.safetensors ... in directory gpt2`). Only bare ids
  collided — `gpt2-medium`, `facebook/opt-125m` etc. were never affected.

### NNsight engine (`--engine nnsight`)
See §7. `--engine manual` remains the default and is byte-for-byte unchanged.

### Backward compatibility
- Any 12-layer checkpoint (`gpt2`, `facebook/opt-125m`, `EleutherAI/gpt-neo-125m`) under the
  default `--layer-mode scaled` produces the **same** band (4–11) as before. Only ≥13-layer models
  see the new depth-aware band.
- **Intervention (i)/(j).** GPT-2 small's EPE₀ has exactly three massive coordinates
  (`{138, 378, 447}`), so the new outlier-based identification returns that same set and GPT-2
  small's `int_i`/`int_j` numbers are **byte-for-byte unchanged**. Models whose massive-coordinate
  count differs from 3 (e.g. `gpt2-medium` → 6) get corrected `int_i`/`int_j` values — this is the
  intended fix, not a regression; the exact set is recorded in `run_config.json`. Re-run all sizes
  so a family's Table 1 is internally consistent.

### Verification (offline, tiny random models — HF weights are network-blocked in the dev container)
- All harnesses compile and expose the new flags.
- `compute_band` correct at every scale (12→[3,11), 24→[3,23), 36→[3,35], 48→[3,47]); `fixed`→[3,11).
- `compute_bos_attention_metric` band override averages exactly the requested layers.
- E4 runs end-to-end on a 24-layer model with the scaled band (identity assert passes;
  decomposition `a_full` == real baseline over the band). **Real weight numbers must be produced
  on GPU** — this container cannot download models.

## 5. Caveats & gotchas

- **`opt-2.8b` → `opt-2.7b`.** The 2.8B id does not exist on the Hub.
- **OPT model guard.** The OPT harness rejects `facebook/opt-350m` at load (it is post-LayerNorm
  and projects the word-embedding dimension, so it is not comparable to the pre-LN circuit).
  All listed OPT sizes (125m/1.3b/2.7b/6.7b/13b) are pre-LN and accepted.
- **GPT-Neo has no query bias.** Intervention **(b) No Query Bias** is a structural no-op on
  GPT-Neo (matches baseline (a)); the positional interventions (c–e, h, i) remain meaningful.
- **Qwen2.5 is RoPE.** There is no additive EPE, so the positional interventions are reframed as
  RoPE position-id manipulations (see the README Qwen section). The harness requires the learned
  query bias (`q_proj.bias`); all listed Qwen2.5 sizes have it. `--dtype auto` (Qwen-only) picks
  fp16 on CUDA / fp32 on CPU.
- **Precision axis.** fp32 is used wherever it fits (matching the paper's SEs). The largest models
  (`opt-6.7b`, `opt-13b`, `Qwen2.5-7B`, `Qwen2.5-14B`) run in fp16/bf16 to fit VRAM — record the
  dtype with each result. The **relative** metric (% of baseline) is robust to precision even
  where absolute BOS attention shifts slightly; report both and note the dtype.
- **Band change vs. prior runs.** Any earlier E1/E2 numbers for ≥13-layer models used the fixed
  4–11 band; under the new `scaled` default they will differ (that is the intended fix). 12-layer
  models are unchanged. Re-run all sizes so the sweep is internally consistent.

## 7. The NNsight engine (`--engine nnsight`) and what parity found

### Why

The harnesses in this experiment do not use HuggingFace's forward pass. They re-implement the
transformer by hand — reading raw weight tensors off the modules (`attn.c_attn.weight.t()`),
recomputing attention, and (for Qwen) re-implementing RoPE and GQA — and run the real forward
only once per sentence, to fire two embedding hooks whose output is then discarded.

`--engine nnsight` runs the **real** forward under [NNsight](https://nnsight.net/) and applies
every intervention as an activation edit inside `.trace()`, reading attention probabilities from
the model's own eager attention (`h[i].attn.output[1]`). The manual path is kept as the reference
implementation and remains the default; `--verify-parity` cross-checks them.

### Expressing weight edits as activation edits

NNsight intervenes on activations, not weights, so the three weight-space interventions are
re-expressed algebraically — exactly, not approximately:

- **(b) No Query Bias.** `q = x·Wqᵀ + b_Q`, so zeroing `b_Q` is exactly subtracting `b_Q` from
  the query slice of the projection output.
- **(i)/(j) Zero Wk columns.** `k = x·Wkᵀ + b_k`; zeroing the input-columns `S` of `Wk` equals
  `k − x[..., S] · Wk[:, S]ᵀ`. For GPT-2's fused Conv1D, `Wk[:, S]ᵀ` is `c_attn.weight[S, H:2H]`.

Both are verified against genuine weight edits (deviation ~1e-8). One subtlety: the (j) random
control draws **with replacement**, and while zeroing a weight column twice is idempotent,
*subtracting its contribution twice is not* — the columns are de-duplicated at the edit site. A
naive implementation is wrong by ~1.5e-3. (At the actual E1/E2 configs with seed 42 no duplicate
is drawn, so this changes no published number; it prevents a latent corruption at other seeds.)

### Parity results (real weights, fp32, all 10 interventions)

| Model | max abs BOS-metric deviation | Verdict |
|---|---:|---|
| `gpt2` | 2.1e-07 | pass |
| `facebook/opt-125m` | 3.1e-07 | pass (several rows bit-identical) |
| `EleutherAI/gpt-neo-125m` | 3.3e-06 | pass |
| `Qwen/Qwen2.5-0.5B` | 1.0e-07 | pass **after the `rope_theta` fix below** |

For `gpt2` the two engines produce **identical Table-1 CSVs at 6 decimal places**. That is the
headline reproducibility result: the paper's hand-rolled forward is faithful to the real model.

The gate is the **BOS metric**, not raw attention probabilities. On GPT-Neo, `(d)` deviates by
~4e-2 per attention cell while its BOS metric agrees to ~3e-6. That is not a defect: GPT-Neo
omits the `1/sqrt(head_dim)` scale, so its logits are ~8× larger and its softmax is near one-hot
(measured mean max-per-row ≈ 0.97). A layer-1 rounding difference then amplifies chaotically with
depth — measured, the layer-0 deviation is *exactly* zero and grows monotonically to ~1e-2 by
layer 8. Individual cells are chaotic under any perturbation; the metric, an average over heads,
second-half tokens and the layer band, is not. Gating per-cell would flag the model's own physics
as a bug.

Parity is **fp32-only**. In fp16/bf16 the two paths are different algorithms rather than rounding
variants — GPT-Neo upcasts q/k to fp32 inside attention (`modeling_gpt_neo.py:105-107`) and
OPT/Qwen softmax in fp32, while the manual path does neither — so the gate downgrades to advisory.

### 🔴 What parity found: a silently wrong RoPE theta in the Qwen harness

`transformers` 5.x moved `rope_theta` into `config.rope_parameters`. `_model_geometry` read it as
`float(getattr(cfg, "rope_theta", 10000.0))`, so under the pinned `transformers==5.3.0` it
silently returned the **10000.0 default** where Qwen2.5's true value is **1e6**. Every rotation
frequency in the manual RoPE was wrong. Nothing raised; `load_qwen` printed the same fallback, so
the logs corroborated the bug rather than exposing it.

`--verify-parity` failed 9/10 interventions at `max|d| attn = 1.000e+00` — the maximum possible
for a probability. The failure signature named the cause by itself: **`int_h` was the only passing
row, and it is the only intervention that sets every position id to 0**, where theta cannot matter
(cos=1, sin=0 for any theta). Everything depending on theta was wrong; the one thing that did not
was exact.

Measured impact on `Qwen2.5-0.5B` (3 sentences, fp32 — indicative; a full re-run is still owed):

| | θ=1e4 (bug) | θ=1e6 (correct) |
|---|---:|---:|
| Baseline (a), absolute BOS attention | 0.5262 | 0.5038 (**4.4% relative error**) |
| (g) No MLP, % of baseline | 7.4% | **12.0%** (+4.6 pp) |
| (h) No PE, % of baseline | 89.6% | **93.6%** (+4.0 pp) |
| (b) No Query Bias, % of baseline | 9.8% | 8.8% (−1.0 pp) |
| (c)/(d)/(e)/(i)/(j) | — | shift < 1 pp |

The qualitative cross-architecture conclusions survive, but the published Qwen numbers are wrong
and (g)/(h) move by ~4–5 pp. Note (h)'s *absolute* value is identical either way — theta cannot
matter at position id 0 — yet its percentage moves, because the baseline it is divided by moved.

`resolve_rope_theta()` now reads `config.rope_parameters["rope_theta"]` (5.x) then
`config.rope_theta` (4.x) and **raises rather than defaulting**: the silent fallback is precisely
what caused this. `_model_geometry` also now rejects non-default `rope_type`, since the manual
RoPE implements the plain formulation only (no `attention_scaling`, no yarn/linear remapping) and
would be quietly wrong for scaled checkpoints. `--engine nnsight` has no such limitation.

**Caveat.** `transformers` 4.x *did* expose `.rope_theta`, so the recorded Qwen numbers may
predate the 5.3.0 pin rather than having been wrong when published. Under the current pin the
manual Qwen path was wrong regardless. **The five Qwen2.5 checkpoints × 3 seeds still need
re-running** before `docs/E1-E2_Summary.md`'s Qwen table can be trusted.

### NNsight 0.7 constraints worth knowing

Three behaviours the engine is built around, found while probing:

1. **Envoy accesses must follow execution order** (`pre_ln → q/k proj → attn → mlp`). Reading
   `attn.output` after touching `mlp.output` raises `MissedProviderError`.
2. **`attn_implementation="eager"` is load-bearing**, not vestigial. Under `sdpa` the eager
   attention path is skipped and `attn.output[1]` is `None`. Asserted at engine init. A locally
   constructed model (e.g. a tiny test config) defaults to `sdpa` and needs
   `set_attn_implementation("eager")` explicitly.
3. **An explicit `attention_mask` must accompany `position_ids`.** `masking_utils` treats any
   position-id step ≠ 1 as a packed-sequence boundary and ANDs a block-diagonal mask into the
   causal mask; Qwen's (h) (all-zero position ids) would otherwise silently degenerate to an
   *identity* mask. The engine always passes an explicit mask.

Also arch-specific: **OPT nulls `attn_weights` unless `output_attentions=True`** is passed
(GPT-2/Neo/Qwen return them unconditionally), and OPT's FFN output is `[B*S, H]` because
`OPTDecoderLayer` reshapes before `fc1`. Both are handled by the `ArchSpec`, not by forking the
engine.
